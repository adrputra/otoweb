# Database Foundation

Status: implemented in Phase 3 (F003). Source of intent:
`docs/ROADMAP.md` §8–§17 and `specs/002-database-foundation/`.

The project uses **Supabase** as the production PostgreSQL platform, **Drizzle
ORM** for the typed schema and queries, and **plain PostgreSQL migrations**
generated by Drizzle Kit and committed under `db/migrations/`.

## What exists

| Artifact | Purpose |
|---|---|
| `db/schema.ts` | Typed Drizzle schema for the seven tables and their enums/relations |
| `db/client.ts` | Lazy server-only Drizzle client over `postgres` (Supabase pooler compatible) |
| `db/migrate.ts` | Applies checked-in migrations over `DATABASE_URL` |
| `db/seed-core.ts` | Idempotent seed function and legacy mock-data mapping |
| `db/seed.ts` | CLI wrapper for the seed |
| `db/migrations/**` | Generated PostgreSQL migration SQL and journal |
| `drizzle.config.ts` | Drizzle Kit schema/migration configuration |
| `supabase/config.toml` | Minimal Supabase CLI project configuration |
| `lib/supabase/client.ts` | Browser-safe Supabase client factory (no auth flow in this phase) |
| `tests/unit/db/database-foundation.test.ts` | Executes migrations + seed against an empty embedded PostgreSQL database |

## Schema

All primary keys are UUIDs (`gen_random_uuid()`). All timestamps are
`timestamptz`. Tenant-owned tables have a `tenant_id` foreign key to
`tenants.id` with `ON DELETE CASCADE`.

```text
tenants
├── tenant_domains        (1:N)
├── tenant_members        (1:N) ── profiles (N:1)
├── showroom_settings     (1:1)
└── vehicles              (1:N)
    └── vehicle_images    (1:N)

profiles ── tenant_members (1:N)
```

### `tenants`

`id`, `name`, `slug` (unique), `status` (`active`/`suspended`/`trial`/
`disabled`), `plan`, `theme`, `created_at`, `updated_at`.

### `tenant_domains`

`id`, `tenant_id`, `hostname` (globally unique), `type`
(`platform_subdomain`/`custom_domain`), `status`, `verified_at`, `created_at`.
Indexed by tenant.

### `profiles`

`id`, `full_name`, `avatar_url`, `created_at`, `updated_at`. The id is intended
to match a Supabase Auth user id once authentication is implemented; this phase
does not create auth identities.

### `tenant_members`

`id`, `tenant_id`, `user_id` (references `profiles.id`), `role`
(`platform_admin`/`owner`/`staff`), `status`, `created_at`, `updated_at`.
Unique on (`tenant_id`, `user_id`); indexed by tenant.

### `showroom_settings`

One row per tenant (`tenant_id` unique). Stores display name, tagline,
description, logo/favicon/hero URLs, primary/secondary colours, phone, WhatsApp,
email, address, city, province, postal code, Google Maps URL, Instagram/TikTok/
Facebook URLs, opening hours, SEO title, SEO description, and timestamps.

F009 (Phase 9) adds no column: the settings editor, logo/hero uploads, public
theming, and SEO metadata consume these existing fields. `favicon_url` remains
unused because the roadmap does not list it as editable.

### `vehicles`

`id`, `tenant_id`, `slug`, `brand`, `model`, `variant`, `year`,
`transmission` (`AT`/`MT`/`CVT`), `fuel_type`
(`bensin`/`diesel`/`hybrid`/`listrik`), `body_type`, `engine_capacity`,
`mileage`, `color`, `price`, `original_price`, `plate_region`,
`tax_expiry_date`, `description`, `status`
(`draft`/`available`/`reserved`/`sold`/`archived`), `featured`, `location`,
`features` (JSONB string array), `owner_count`, `documents` (JSONB), and
created/updated/published/reserved/sold timestamps.

Unique on (`tenant_id`, `slug`); indexed by tenant and status. `owner_count` and
`documents` are nullable compatibility columns that retain the existing mock
detail-page content; they do not add behaviour in this phase.

### `vehicle_images`

`id`, `tenant_id`, `vehicle_id`, `provider`, `provider_asset_id`, `url`, `alt`,
`position`, `is_cover`, `width`, `height`, `created_at`. Indexed by tenant and
vehicle. `alt` is retained for accessibility and because the mock images already
carry it.

F008 uses the table as-is (no migration). The service keeps `position`
contiguous and exactly one `is_cover` per vehicle. `provider_asset_id` is the
deterministic Cloudinary public id (or the fake provider path). On vehicle or
photo deletion, only assets whose provider matches the active media provider are
candidates, and an asset is destroyed only when no row in any tenant references
it; see `docs/MEDIA.md` for the full policy.

## Enum and status mapping

PostgreSQL enums: `tenant_status`, `tenant_domain_type`, `tenant_member_role`,
`vehicle_transmission`, `vehicle_fuel_type`, `vehicle_status`.

The production vehicle status replaces the legacy split between `availability`
and `publication`:

| Mock `publication` | Mock `availability` | Database `status` |
|---|---|---|
| `draft` | any | `draft` |
| `archived` | any | `archived` |
| `published` | `available` | `available` |
| `published` | `reserved` | `reserved` |
| `published` | `sold` | `sold` |

`published_at` is set for published vehicles. `reserved_at` and `sold_at` are
set when the mapped status is reserved/sold and the vehicle is published.

## Development seed

The seed is idempotent and uses deterministic UUIDs. It creates:

- **Prima Auto Gallery** (`prima-auto-gallery`, active, starter, premium):
  domain `prima.otoweb.id`, owner profile/membership, showroom settings mapped
  from `data/index.ts`, all 12 mock vehicles, and one image per vehicle.
- **Tenant B Test Showroom** (`tenant-b-test-showroom`, trial): domain
  `tenant-b.otoweb.id`, owner profile/membership, and distinct showroom
  settings. It intentionally has no legacy vehicle catalogue.

The twelve Prima vehicles are mapped from `data/index.ts`, preserving slugs,
brand/model/variant/year, price, original price, mileage, colour, engine
capacity, plate region, tax expiry, description, features, featured flag,
availability/publication semantics, owner count, document flags, and image URL/
alt/order/cover metadata.

Re-running the seed upserts the same rows; it does not truncate the database and
does not duplicate tenants, vehicles, or images.

## Environment

Only placeholders are committed in `.env.example`:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=your-anon-key
DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres
```

- `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` are
  browser-safe project values.
- `DATABASE_URL` is server-only and is used by Drizzle migrations and seeds.
- Never commit a real database password or the Supabase service-role key.

The migration and seed CLIs load `.env.local` and `.env` when present; real
environment variables take precedence. Missing `DATABASE_URL` produces an
explicit error naming the variable.

## Commands

```bash
pnpm db:generate   # regenerate SQL after a schema change
pnpm db:migrate    # apply unapplied migrations over DATABASE_URL
pnpm db:seed       # upsert the development dataset
pnpm db:setup      # migrate, then seed
pnpm db:verify     # run only the database test suite
pnpm test          # full unit suite, including the database proof
```

## Production Supabase path

1. Create a Supabase project and copy its database connection string into
   `DATABASE_URL` (server-only). For a transaction pooler, the client already
   sets `prepare: false`.
2. Copy the project URL and anon key into the two `NEXT_PUBLIC_SUPABASE_*`
   variables.
3. Run `pnpm db:migrate`, then `pnpm db:seed` for development data (do not seed
   production customer data).
4. Verify in the Supabase SQL editor:

   ```sql
   select table_name
   from information_schema.tables
   where table_schema = 'public'
     and table_name in (
       'tenants', 'tenant_domains', 'profiles', 'tenant_members',
       'showroom_settings', 'vehicles', 'vehicle_images'
     );

   select name, slug, status from tenants order by name;
   select count(*) from vehicles;
   select count(*) from vehicle_images;
   ```

### Local Supabase CLI path

`supabase/config.toml` is committed for teams that have Docker and the Supabase
CLI. `supabase start` is **not** runnable in this repository's current
environment (no Docker daemon, no Supabase CLI, no `psql`). The embedded
verification path below is the executed proof.

## Embedded verification path

`tests/unit/db/database-foundation.test.ts` runs in the `node` environment with
`@electric-sql/pglite`, an embedded PostgreSQL engine. It:

1. Creates a fresh in-memory database.
2. Applies the checked-in migration SQL from empty.
3. Asserts the seven tables, enum types, tenant foreign keys, and a safe second
   migration pass.
4. Runs the real `seedDatabase` function.
5. Asserts both tenants, their domains/profiles/memberships/settings, all twelve
   vehicles and images, mock parity, draft/reserved/sold/featured semantics, and
   idempotency on a second seed.

This proves the committed SQL and seed logic without Docker, the Supabase CLI, a
local PostgreSQL server, or network access.

## Deferred to later phases

- **Authentication and invitations** (Phase 4): the schema stores profiles and
  memberships, but no auth flow or session handling is implemented.
- **Row-level security and tenant enforcement** (Phase 5): implemented in
  `db/migrations/0001_tenant-isolation.sql`, `lib/tenant/`, and
  `tests/unit/tenant/`; see `docs/TENANCY.md`. The F003 tables and seed shape are
  unchanged.
- **Public database reads** (Phase 6): implemented in `lib/public/` and
  `lib/repositories.ts`; the public home, inventory, detail, related, featured,
  and showroom data read tenant-scoped rows. Public runtime modules no longer
  import `data/index.ts`. See `docs/PUBLIC_SITE.md`. The F003 tables and seed
  shape are unchanged.
- **Showroom settings administration** (Phase 9): implemented in
  `specs/008-showroom-settings/`, `lib/admin/showroom-settings-*`,
  `lib/theme.ts`, and the public routes. No schema change.
- **Leads** (Phase 10): not in this feature's explicit table list.
- **Cloudinary upload lifecycle** (Phase 8): `vehicle_images` stores provider
  metadata, but upload is not implemented.
