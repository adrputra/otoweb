# Research: Database Foundation

**Feature**: `002-database-foundation`  
**Date**: 2026-10-18

## Decision 1 — Supabase as the PostgreSQL platform, Drizzle as the access layer

- **Decision**: Keep Supabase as the production PostgreSQL platform and add
  Drizzle ORM with `postgres` (postgres.js) for application queries and
  migrations. Add `@supabase/supabase-js` plus a minimal Supabase CLI
  configuration and browser-safe environment placeholders, but do not build an
  auth flow in this feature.
- **Rationale**: The roadmap mandates Supabase, PostgreSQL, and Drizzle. Drizzle
  gives a typed schema that generates plain SQL migrations, which can be applied
  identically to a Supabase database, a local PostgreSQL database, or the
  embedded test engine. A lazy Supabase client factory and `supabase/config.toml`
  establish the platform configuration without exposing service-role credentials
  or implementing authentication ahead of Phase 4.
- **Alternatives considered**: Prisma (not the roadmap choice and adds a
  generated client step); raw SQL only (loses the typed schema and migration
  generation the roadmap asks for); Supabase JS data API for all access (does not
  provide the required PostgreSQL migrations and would spread data access across
  two APIs).

## Decision 2 — Checked-in SQL migrations generated by Drizzle Kit

- **Decision**: Author `db/schema.ts`, configure `drizzle.config.ts`, and commit
  the generated `db/migrations/**` SQL and metadata. Apply migrations at runtime
  with Drizzle's migrator over `postgres.js`; the same generated SQL is executed
  by the test suite against an empty PGlite database.
- **Rationale**: A checked-in SQL migration is the auditable artifact the
  acceptance criterion ("schema migration works from empty database") refers to.
  Generating it from the typed schema prevents schema/migration drift. Drizzle's
  journal ensures re-runs only apply new migrations.
- **Alternatives considered**: `drizzle-kit push` only (no migration history or
  reproducible empty-database path); hand-written SQL only (no typed schema);
  runtime schema sync (not deterministic in production).

## Decision 3 — Embedded PGlite for executable verification

- **Decision**: Add `@electric-sql/pglite` and a Vitest test in the `node`
  environment that creates a fresh in-memory PostgreSQL instance, applies the
  checked-in migrations from empty, runs the real seed function, and asserts the
  schema and rows. Document the production Supabase path separately.
- **Rationale**: The environment has no Docker daemon, no Supabase CLI, and no
  `psql`/local PostgreSQL server, so a claim that the migration and seed work
  would otherwise be untested. PGlite is PostgreSQL compiled to WebAssembly, not
  a SQLite imitation; it executes the same DDL, enums, UUIDs, JSONB, foreign
  keys, and constraints. It runs inside the existing `pnpm test`/`npm test`
  command with no external service.
- **Alternatives considered**: SQLite (not PostgreSQL; would not prove enum,
  JSONB, UUID, or PostgreSQL DDL behavior); testcontainers/Docker (unavailable);
  a remote Supabase test project (requires credentials and network, and would
  not be deterministic in CI); no test (violates the evidence/acceptance rules).

## Decision 4 — Schema shape and legacy mock-data mapping

- **Decision**: Follow the roadmap database chapters (§8–§17) for table fields.
  Use UUID primary keys, `tenant_id` on tenant-owned tables, PostgreSQL enums
  for tenant status, domain type, member role, transmission, fuel type, and
  vehicle status, and JSONB for vehicle features. Keep `owner_count` and
  `documents` as nullable compatibility columns because the approved vehicle
  detail page displays ownership and the mock records carry document data. Map
  legacy `availability` + `publication` into the single production `status`:
  `draft` publication -> `draft`; `archived` -> `archived`; otherwise the
  availability value (`available`/`reserved`/`sold`).
- **Rationale**: This preserves both the roadmap's production schema and the
  existing displayed content. A single `status` avoids the roadmap's warned
  against inconsistency between two overlapping state fields.
- **Alternatives considered**: Drop `owner_count`/`documents` (loses visible
  mock content and makes a later database-driven detail page incomplete);
  keep `availability` and `publication` columns (duplicates state and conflicts
  with the roadmap's status model); normalize features into a table (roadmap
  explicitly prefers JSONB for MVP).

## Decision 5 — Deterministic, idempotent seed

- **Decision**: Put the pure seed logic in `db/seed-core.ts` with deterministic
  UUID constants for tenants, profiles, memberships, domains, settings,
  vehicles, and images. Insert with `onConflictDoUpdate` on the primary key so a
  re-run updates the same rows instead of duplicating them. Add thin CLI
  wrappers (`db/migrate.ts`, `db/seed.ts`) that load local env files and use the
  production `DATABASE_URL`.
- **Rationale**: Idempotency is an explicit edge case and is easy to prove with
  stable IDs. Deterministic IDs also let tests reference exact rows without
  matching by display name. Upserts make seed corrections repeatable without
  truncating unrelated data.
- **Alternatives considered**: Random UUIDs with slug-based upserts (more
  complex conflict targets and image ordering); delete-then-insert (destructive
  and unsafe against a real database); `onConflictDoNothing` (safe but ignores
  seed corrections).

## Decision 6 — Environment and secret handling

- **Decision**: Extend `.env.example` with placeholders for
  `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and a Supabase
  local-default `DATABASE_URL`. Keep real `.env*` files ignored. Migration and
  seed scripts fail with a clear message when `DATABASE_URL` is absent. The
  service-role key is never added.
- **Rationale**: The acceptance requires Supabase configuration without real
  credentials. The anon key and project URL are browser-safe; the database URL
  is server-only. A local Supabase default makes the documented production path
  concrete without pretending the local stack runs here.
- **Alternatives considered**: Commit a working database URL (forbidden and
  environment-specific); require a service-role key (unnecessary for database
  migrations and dangerous); silently default to a production URL (unsafe).

## Decision 7 — Defer auth, RLS, and leads

- **Decision**: Create only the seven required tables. Create the membership and
  tenant columns that later phases need, but do not add authentication, session
  handling, permission helpers, RLS policies, or the `leads` table.
- **Rationale**: The feature payload explicitly forbids auth, multi-tenant
  enforcement, and backend APIs beyond the database layer. The roadmap assigns
  auth to Phase 4, RLS/isolation to Phase 5, and leads to Phase 10. `leads`
  appears in the roadmap's table overview but not in this feature's explicit
  table list.
- **Alternatives considered**: Implement RLS now (out of scope and impossible to
  validate without auth identities); add `leads` (scope creep beyond the
  acceptance table list).

## Decision 8 — Verification commands

- **Decision**: Add `db:generate`, `db:migrate`, `db:seed`, and `db:setup`
  scripts. Verification is part of the normal test suite:
  `pnpm test` (and `npm test`) executes the PGlite migration/seed test. The
  checkpoint also runs `npx tsc --noEmit`, `pnpm lint`, `pnpm typecheck`,
  `pnpm test`, and `pnpm build`.
- **Rationale**: `npm test` is the configured outer validation command; putting
  the database proof inside it guarantees the roadmap acceptance is exercised
  wherever the project's tests run. Separate `db:*` scripts document and support
  the production Supabase path.
- **Alternatives considered**: A separate opt-in database test command (would let
  the configured gate pass without proving the migration); shell-only scripts
  (no assertions on data parity).
